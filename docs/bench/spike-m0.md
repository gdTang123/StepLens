## 2. 原型说明（`/workspace/bench/src/spike.cpp`）

按架构文档方案 B 的加载流水线写的命令行程序，每个样例单独一个进程、串行运行：

1. **读取**：`STEPCAFControl_Reader::ReadStream()` + 自定义 `ProgressStreamBuf`（每次 `underflow()` 读 1 MiB，统计字节、检查取消标志，取消时返回 EOF）。读取选项按 `LoadOptions` 默认：颜色、名称、SHUO 开；图层、校验属性、PMI、材料、视图关。IGES 用 `IGESCAFControl_Reader::ReadFile()`。
2. **转换**：`Transfer(doc, progress)`，进度用 `Message_ProgressIndicator` 子类（`Show()` 记录进度，`UserBreak()` 返回取消标志并记录两次调用之间的最长间隔）。
3. **释放读取器**：销毁读取器后调用 `malloc_trim(0)`（Linux 下对应 Windows 的 `_heapmin()`）。
4. **建模型**：遍历 XCAF 装配，按原型（非装配的形状标签）去重，统计实例数、面数、实体数。
5. **三角化**：对每个原型按 5.5.1 公式算弦高 `clamp(c × 原型包围盒对角线, 0.005, c_g × 全局对角线)`；面数 ≤ 2000 的原型用 `OSD_Parallel::For` 按原型并行（`InParallel=false`），> 2000 面的大原型串行逐个 `InParallel=true`（即 5.4 方案 B）。每级之前用 `BRepTools::Clean` 清掉旧网格。
6. **内存**：读 `/proc/self/status` 的 `VmRSS`/`VmHWM`；每个阶段开始前写 `/proc/self/clear_refs` 重置峰值，所以每个阶段的峰值是独立的。**进程全程峰值 = 各阶段峰值的最大值**。

注意：全局包围盒是把所有原型（未施加实例变换）放在一起算的，是全局尺寸的近似值；这只影响弦高上限 `c_g`，不影响结论的数量级。

| X-01 | 1587 | 1470 | 1371 | 519 | 1131 | **1587** | 5.6× |

观察：
1. **峰值大多出现在读取阶段**（不是架构 5.6.1 估计的转换阶段），约为文件大小的 4.6–5.7 倍。实测峰值 1.1–1.9 GB，**远低于** 5.6.1 估计的 3–5 GB。
2. **释放读取器 + `malloc_trim` 很有效**：RSS 从 0.97–1.40 GB 降到 0.34–0.52 GB（STEP），即释放约 58–70%。（IGES 7.9.3 只从 1500 降到 1169 MB。）
3. **单个巨型原型的文件（X-04、X-05，整个文件 1 个原型、3.7–4 万面、无实体只有壳）三角化时内存大涨**：X-05 网格只有 63 万三角形，但网格阶段 RSS 从约 0.4–0.5 GB 涨到 1.9 GB，成为全程峰值。原因推测是 `BRepMesh` 在一个形状内按面并行时的临时数据（未深入定位）。按原型拆分或限制大原型并行度可以再看。
4. 网格阶段的峰值是在先跑过粗、细两级（各自清理后）再跑方案 B 时测的，可能含有堆碎片的残留，**略偏高**。

## 5. 进度和取消实测

### 5.1 读取阶段：自定义 streambuf

| 检查项 | 结果 |
|---|---|
| `ReadStream` 是否先把整个流读进内存？ | **不是**。字节是边读边解析的：M-04（40 MiB）的字节进度在 0.86 s 内从 0 线性走到 100%，读取峰值内存随已读字节增长（X-02 取消在 90% 时峰值 1054 MB，完整读取 1876 MB） |
| 字节进度是否线性？ | 在"流读取"这一段是线性的（每 5% 的时间间隔基本相同） |
| 字节进度能否代表整个读取阶段？ | **不能**。流读完之后，OCCT 还要花 **55–71%** 的读取时间建实体模型，这段时间 streambuf 不再被调用，没有进度：L-03 6.3 s、X-01 6.4 s、X-02 7.5 s、X-03 10.8 s、X-04 10.5 s、X-05 9.8 s |
| 提前返回 EOF 能否取消？ | **能**。`ReadStream` 返回 `IFSelect_RetError`(3)，只输出 1 行 `ERR StepFile : ... unexpected end of file`，不刷屏、不崩溃 |
| 取消延迟（请求取消 → `ReadStream` 返回） | X-02 在 10% / 50% / 90% 处取消：**23 / 44 / 72 ms**；其中"请求 → streambuf 返回 EOF"约 17–19 ms（解析器吃完手上 1 MiB 的时间），其余是解析器收尾 |
| 稳定性 | M-04 在 2%–98% 之间随机位置取消 **20 次**：全部正常返回，延迟 23–40 ms（中位 26 ms），无崩溃 |
| 取消后内存 | 释放读取器后 RSS 回到 32 MB（进程启动时 26 MB），20 次之间没有累积增长 |
| 盲区 | 如果取消发生在"流已读完、实体模型还在建"那段（6–11 s），streambuf 已经没有机会插手，只能等 `ReadStream` 自己返回。**本次没有专门测这段的取消**，延迟上限按结构推断等于这段的剩余时间 |

### 5.2 转换阶段：`Message_ProgressIndicator::UserBreak()`

| 检查项 | 结果 |
|---|---|
| 取消是否生效？ | **生效**。`Transfer` 返回 false，没有异常，没有崩溃。注意：取消后进度指示器会跳到 100%，界面应忽略这次跳变 |
| 取消延迟（X-02，按转换耗时的 20% / 50% / 80% 触发） | **3 / 10 / 17 ms** |
| 取消后释放（关闭文档 + 释放读取器 + trim） | 1.38 / 1.23 / 1.94 s，RSS 回到约 41 MB |
| 两次 `UserBreak()` 之间的最长间隔（完整转换） | X-01 1.85 s，X-02 1.13 s，X-03 2.63 s，X-04 1.18 s，X-05 1.45 s，**L-03 13.73 s**（转换开始后约 26–40 s，进度停在 12.6%），M-04 1.8–1.9 s。**这就是最坏取消延迟** |
| M-04 按时间取消的实例 | 在转换第 6.0 s 请求取消，正好落进 1.9 s 的空档，**1.32 s 后**才返回 |
| 进度是否线性？ | **严重不线性**。例：X-03 转换 47.7 s，前 32 s 进度一直是 0%；X-04 转换 36.1 s，从第 3 s 到第 31 s 一直停在 3–4%，第 33 s 才跳到 50%，之后直接到 100%；X-05 类似。只有 IGES（7.9.3）的进度大致线性 |

### 5.3 对设计的影响

1. 读取阶段：**streambuf 方案可用**，取消在流读取期间 < 0.1 s；但读取阶段的进度要分两段——"读文件"（字节进度，约占读取时间 30–45%）+"解析结构"（无进度，显示忙碌 + 已用时间）。
2. 转换阶段：`UserBreak` 取消可用，但最坏延迟实测 13.7 s；**OCCT 进度位置不能直接驱动进度条**，建议用"按文件大小预估的耗时"做时间进度，OCCT 位置只作为下限。
3. "点击取消 → 界面恢复 ≤ 1 s" 只能靠 **5.3 节的软取消**（界面先恢复，后台等 OCCT 返回再释放）实现；"后台 ≤ 10 s 停止"对 L-03 这类文件**达不到**。

## 6. X-07 超大 IGES

- 下载：成功（`https://twindisc.com/downloads/PX13226.IGS`，266,541,902 字节，与 samples.md 一致），保存在 `/workspace/samples/dl/PX13226.IGS`。
- **OCCT 8.0.1：转换阶段段错误（SIGSEGV），5 次运行全部崩溃**（下面 3 种参数 + 栈 unlimited + gdb 下各 1 次）：
  1. 正常参数（颜色、名称开，挂进度）：读取 4.6 s 成功（峰值 881 MB），转换中崩溃；
  2. 不挂进度（`Transfer(doc)`）：仍崩溃（排除我们的进度桥）；
  3. 关掉颜色和名称读取：仍崩溃；
  4. 把栈限制设成 unlimited：仍崩溃（排除栈溢出）。
  - gdb 回溯：崩溃点在 `IGESCAFControl_Reader::Transfer(...)`（`libTKDEIGES.so.8.0`）内部，从总耗时推算约在转换开始后 50 s。没有带调试符号，未定位到具体行。
- **OCCT 7.9.3：成功**。读取 4.2 s，转换 64.4 s，释放 1.5 s，方案 B 网格 2.9 s，合计 73.6 s；峰值 1.5 GB；32,711 个顶层面（没有实体）；进度大致线性，`UserBreak` 最长间隔 0.59 s。
- IGES 读取用的是 `ReadFile()`（IGES 读取器没有单独测流式读取和读取阶段取消；读取只有 4 s，影响不大）。
- 只测了这一个 IGES 超大文件；X-06、X-08 没有下载。

## 7. Go / No-Go 结论

**有条件 Go（继续按方案 B 交付）。**

Go 的依据：
- OCCT 8.0.1 的 STEP 链路在全部 6 个指定样例上成功，单次全流程 56–87 s，峰值 1.1–1.9 GB，在本机（服务器 vCPU、可用内存只有约 6.5 GB）上就已经低于方案 B 超大档"≤ 180 s、≤ 10 GB"的目标；
- streambuf 取消、`UserBreak` 取消都能干净返回，内存能回落；
- 三角形总量在目标内，三角化只占几秒。

必须满足的条件（否则对应部分 No-Go）：
1. **IGES：8.0.1 在 X-07 上崩溃，是当前唯一的阻断项。** 建议 T05 开始前（1 天内）在 Windows 的 vcpkg 8.0.1 构建上复测 X-07；仍崩溃则 (a) 向 OCCT 提 issue 并附文件链接，(b) 项目整体退回 7.9.3（同一份代码已对 7.9.3 编译通过），或 (c) IGES 走子进程加载隔离崩溃。在这之前，**"IGES 超大文件"不能承诺**。
2. **取消按软取消实现**：界面 ≤ 1 s 恢复；后台停止时间不承诺 10 s（见第 8 节修订）。
3. **在一台真实团队电脑（Windows + MSVC）上复测 X-02 和 L-03**，用于把本报告的外推换成实测。
4. 500 MB–1 GB 没有真实样例，需要 T03 的合成文件或老板提供的真实文件验证（建议从 T03 的 B 方案里把 stepgen 提前，或直接要 1–2 个老板的真实文件）。

## 8. 第 6 节性能目标修订建议（方案 B）

### 8.1 外推方法（**以下全部是外推，不是实测**）

- 时间：按 X-01～X-05 的"合计 s/MiB"（0.160–0.275）线性外推；L-03 类"转换特别慢"的文件按 0.521 s/MiB 单列。读取 + 转换是单线程，不随核数变化。
- 内存：按 X-01～X-05 的"全程峰值 / 文件大小"（5.0–8.6 倍）线性外推。
- 风险：实体数、B 样条数量与文件大小不严格成正比，转换耗时也可能超线性（例如 L-03）；本机与团队电脑单核性能差异未知。

| 文件大小 | 首次打开到出图（方案 B 单级网格，不含 GUI 出图） | 典型峰值内存 | 读取后半段无检查点时长 |
|---|---|---|---|
| 实测 225–357 MiB | 56–72 s（L-03 166.7 MiB：87 s） | 1.3–1.9 GB | 6.4–10.8 s |
| **外推** 500 MiB | 约 80–140 s；L-03 类约 260 s | 约 2.4–4.2 GiB | 约 10–22 s |
| **外推** 1 GiB | 约 165–280 s；L-03 类约 530 s | 约 5.0–8.5 GiB | 约 21–45 s |

### 8.2 建议修订值

| 项 | 原目标（6.3 方案 B） | 建议修订 | 依据 |
|---|---|---|---|
| 超大档区间 | 200–400 MiB | 拆成 **超大 200–400 MiB** 和 **特大 400 MiB–1 GiB**（老板的日常文件落在特大档） | 老板确认真实文件 500 MB–1 GB |
| 超大档首屏 = 完整加载 | ≤ 180 s | **≤ 120 s**（实测 56–87 s，留 GUI 出图和 Windows 差异余量） | 第 3 节；按 6.3 规则 max(120, 53.0×1.2+2.2) = 120 |
| 特大档首屏 = 完整加载 | 无 | **500 MiB ≤ 180 s，1 GiB ≤ 360 s**（外推，团队电脑实测后定稿） | 8.1 |
| 超大档峰值内存 | ≤ 10 GB | **≤ 3 GB**（实测 1.1–1.9 GB） | 3.2 |
| 特大档峰值内存 | 无 | **≤ 9 GB @ 1 GiB**（外推 5.0–8.5 GiB）；16 GB 电脑可以打开 1 GB 文件但余量小，**建议 1 GB 文件常用的同事用 32 GB** | 8.1 |
| 打开前内存预估系数 `estimatePeakBytes` | 未定 | **典型 6 × 文件大小，上限 9 ×**（单原型、每面一色的文件取上限） | 3.2：5.0–8.6× |
| 5.9 文件大小上限 | ≤ 400 MiB 正式支持 | ≤ 1 GiB 都允许打开；> 1 GiB 提示建议 32 GB 内存 | 老板确认的真实规模 |
| 取消：界面恢复 | ≤ 1 s | 保持 **≤ 1 s**（软取消） | 5.3 |
| 取消：后台停止并释放 | ≤ 10 s | **≤ 400 MiB：≤ 20 s；1 GiB：≤ 60 s（外推）**；如果要硬性保证，v0.2 做子进程加载 | 实测最坏：读取后半段 6–11 s、转换空档 13.7 s，释放 1.2–1.9 s |
| 进度阶段比例 | 读 45% / 转换 40% / 网格 15% | **读 20%（其中字节进度只占前 40%）/ 转换 70% / 网格+出图 10%**；转换阶段用时间估算驱动 | 3.1、5.2 |
| 粗 / 细网格三角形目标 | 粗 ≤ 300 万、细 ≤ 1000 万 | 保持（实测最多 295 万 / 752 万） | 4 节 |
| 交互帧率 | ≥ 15 FPS（超大） | **暂不修订**，等 Windows 实测；团队电脑有独显，建议验收机改成团队电脑而不是 UHD 630 | 本机无 GPU |

另外建议：
- 二期磁盘缓存（5.7）的优先级提高。特大档首次打开外推要 3–6 分钟，主要是单线程转换，只有缓存能解决"重复打开"。
- 读取完立刻释放读取器 + `_heapmin()` 已经证明有效（RSS 降 58–70%），保持在 T05 中。
